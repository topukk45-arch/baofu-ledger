# 撤销导入：批次依赖链和字段级回滚

> 代码：[`www/import/undo.js`](../../www/import/undo.js)（纯函数，输入存档现在的样子，输出撤销方案）、[`www/import/write.js`](../../www/import/write.js) 的 `recHash`。真正写库由主页面 `JiwenImportStore.undo(方案)` 在一个 IndexedDB 事务里做，写之前先备份。

## 要解决的问题

导入不是一次性的：用户可能 10 月导一次、11 月再导一次，中间还会手动改记录、处理待处理、让 AI 改分类。这时想「撤销 10 月那次导入」，难在两件事：

1. **后来的操作可能建立在这一批之上**。比如 11 月导入时，把一笔账单合并进了 10 月导入的记录；或者 11 月的退款挂在 10 月的原单上。只撤 10 月，11 月那批就会指向不存在的东西。
2. **用户在导入之后亲手改过的东西不能被冲掉**。导入时把一条手记的时间改成了账单时间，用户之后又改了它的备注——撤销时时间要改回去，备注要留着。

## 导入时留下的「凭据」

每次写入（导入、AI 修改、处理待处理……）都在导入记录（log）里记下：

| 字段 | 内容 | 用来 |
|---|---|---|
| `add` | 这批新建的记录 id | 撤销时删掉 |
| `h` | 和 `add` 一一对应的指纹 | 认出新建的记录导入后有没有被改过 |
| `chg[]` | 改过的已有记录：`{ id, was, now }`，`was` 是每个字段改之前的值，`now` 是写进去的值 | 字段级回滚 |
| `cpLen` / `cpEnd` | 对方名单导入前 / 导完时的长度（名单只往后加，编号就是位置） | 名单截断、判断「后来的记录用没用这批新加的名字」 |
| `catsAdded`、`rulesAdded`、`rulesChanged` | 这批新建的分类、存的规则、改过的规则 | 撤销时删 / 改回 |
| `pendTaken` | 这批从待处理池拿走的条目和原来的位置 | 撤销时按原位放回 |

**指纹**：把记录去掉 `id`、`refundOf`（以及不算「用户改动」的 `rv` 待确认标记、`raw` 账单原文、`parts` 几笔合成的一条每一笔的明细）后，按键排序序列化成 JSON，再做 53 位哈希（cyrb53 变体）。键排序保证同样的内容永远得到同样的指纹，和字段写入顺序无关。

## 第一步：算依赖链（`depsOf`）

要撤第 `i` 批，从它之后的每一批 `L` 往后扫，只要 `L` 依赖链上**任何一批**（不只是第 `i` 批），`L` 就进链：

| 依赖原因 | 判断方法 |
|---|---|
| `same` 合并 / 追加了这批碰过的记录 | `L.chg` 里的 id 在 X 的 `add ∪ chg` 里 |
| `ai` AI 修改改过这批的记录 | 同上，且 `L.kind === 'ai'`；或 `L.of === X.b`（AI 修改就是对着 X 做的） |
| `refund` 退款挂在这批的记录上 | L 的记录 `refundOf` 指向 X 碰过的记录 |
| `names` 用了这批新加的对方名 / 支付方式 | L 的记录 `cp` 编号落在 `[X.cpLen, X.cpEnd)` 区间 |
| `cat` 用了这批新建的分类 | L 的记录、规则、分类对照指向 X 的 `catsAdded` |
| `pending` 拿走了这批留下的待处理 | L 的 `pendTaken` 里有 X 的条目 |
| `marker` 用了这批登记的退款记号 | 单号表里 L 的 `RU` 记号对上 X 的 `RW` 记号 |

因为依赖是**传递着算**的（`inChain` 不断变长），A ← B ← C 这种间接依赖也能找出来。最后从新到旧依次撤链上的每一批；确认框用大白话写出「要先撤销之后的 1 次 AI 修改」这类原因。

规则不算依赖：后来的导入用了这批存的规则推荐分类，结果已经写在记录上了，撤规则不影响它们。

## 第二步：撤一批（`undoOne`，在状态的拷贝上改）

**新建的记录**：照删。删之前用指纹比一下，对不上的列进「导入后你改过」，在确认框里告诉用户（不阻止撤销，但让用户知道）。用户挂在这些记录上的退款一起删；已经被用户删掉的跳过。

**改过的已有记录**：一个字段一个字段地看：

```
对 chg.was 里的每个字段 k：
  如果 现在的值 ≠ chg.now[k]     → 用户后来改过，保留，列进 kept
  否则如果 k 是分类、原分类已被删除 → 也保留（不让记录挂在不存在的分类上）
  否则                            → 改回 chg.was[k]（原来没有这个字段的就删掉字段）
```

这样「导入改了时间、用户后来改了备注」的手记，撤销后时间回到原来、备注保留用户改的。

**其余数据**：单号表删掉这批登记的条目；待处理池按 `pendTaken` 原位放回；规则按 `rulesAdded` 删、按 `rulesChanged` 改回（只在规则现在还是导入写的那个值时）；新建的分类没人用了才删；名单如果这批是最后一次导入就截断，不是最后一次就把「导入前长度」交给后一批，以后撤后一批时一起截。

## 怎么保证对

- **全部倒序撤完，存档逐字节回到导入前**：测试里导入几批、中间穿插手动改动，再全部撤销，和导入前的存档逐字节比较（[`tests/z4-import-undo.test.js`](../../tests/z4-import-undo.test.js)；纯计算部分在 [`z3-import-undo-calc`](../../tests/z3-import-undo-calc.test.js)）。
- **性质测试**（[`tests/zZz6-prop-ops.test.js`](../../tests/zZz6-prop-ops.test.js)）：随机组合记账、导入、处理待处理、拆开合并、AI 修改、撤销、恢复备份，每一步检查单号表、待处理池、导入记录、名单、记录之间互相对得上；跑出来的嵌套问题用 [`tests/zZz7-nested-fixes.test.js`](../../tests/zZz7-nested-fixes.test.js) 钉住。
- **老数据兼容**：早期版本的导入记录没有 `h` / `now`，按「没改过」还原，并在确认框里写明。
- **写入是一个事务**：撤销前先备份「撤销前」；写库时版本号变了（期间账本被改过）就拒绝，让用户重新确认；写失败什么都不改，刚写的备份也删掉。
